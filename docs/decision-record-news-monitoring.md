## 1. 背景与约束 (Context)

### 触发场景
*   **信息过载**: 每天手动刷新多个新闻源/网站，效率低下且容易遗漏重要信息。
*   **被动接收**: 希望实现"信息找人"，每天定点获取经过筛选的行业摘要。

### 核心约束
*   **推送渠道**: 必须支持国内 IM（飞书/钉钉/企业微信）。
*   **预算限制**: 零预算（优先开源/自托管方案）。
*   **学习目标**: 希望通过搭建过程理解自动化原理，而非单纯使用黑盒工具。
*   **维护成本**: 个人项目，要求后期维护成本极低。

### 成功标准
*   **MVP**: 脚本能定时抓取 RSS 并推送到飞书群。
*   **进阶**: 支持 AI 摘要、去重、多源聚合。
*   **长期**: 稳定运行，无需频繁人工干预。

## 2. 候选方案 (Options)

| 方案 | 优点 | 缺点 | 适用场景 | 排除/延后理由 |
| :--- | :--- | :--- | :--- | :--- |
| **SaaS (SignalHub/Eclectis)** | 开箱即用，AI 内置 | 不支持飞书，付费，数据不可控 | 预算充足、不想折腾 | ❌ 不支持国内 IM，无学习价值 |
| **Python 脚本 + Cron** | 极度灵活，零成本，完全掌控 | 需自己写解析/调度逻辑 | 快速验证、学习原理 | ⚠️ 长期维护成本随逻辑复杂度上升 |
| **Miniflux + 飞书桥接** | 轻量稳定，资源占用极小 | 无 AI 摘要，需维护两个服务 | 纯 RSS 聚合、低资源环境 | ⚠️ 缺乏 AI 处理能力，扩展性一般 |
| **FreshRSS** | 生态成熟，UI 体验好 | 需 PHP 环境，推送需自写扩展 | 需要完整阅读器体验 | ❌ 部署较重，不符合 MVP 快速验证 |
| **n8n (工作流平台)** | 可视化编排，原生飞书节点，AI 集成 | 学习曲线稍陡，需 Docker | 复杂自动化、长期方案 | ⚠️ MVP 阶段过重，留作进阶方案 |

## 3. 决策与依据 (Decision)

### 最终选择
**"Python 脚本 (MVP) → n8n (长期)" 的分阶段路线**

### 核心依据
1.  **学习曲线平滑**: Python 脚本是"白盒"，能让我亲手处理 HTTP 请求、JSON 解析和 Webhook 发送，彻底理解自动化底层原理。
2.  **快速反馈**: 几十行代码 + 一个 Webhook URL 即可在 5 分钟内跑通 MVP，获得正向反馈。
3.  **可迁移性**: 理解原理后，迁移到 n8n 只是将"代码逻辑"映射为"可视化节点"，学习成本大幅降低。
4.  **灵活性**: Python 脚本可以随时接入 LLM API 做摘要，不受限于特定工具的插件生态。

### 妥协点
*   **牺牲了可视化界面**: 初期没有 Web UI 管理订阅源，需通过代码/配置文件管理。
*   **需自行处理异常**: 网络波动、RSS 格式变化等需自己写 try/catch 和重试逻辑。

## 4. 实施路径 (Roadmap)

### Phase 1: MVP 验证 (本周)
- [ ] 编写 Python 脚本：`feedparser` 抓取 RSS → 格式化 Markdown → `requests` 发送飞书 Webhook。
- [ ] 配置本地 `cron` 或 GitHub Actions 定时触发。
- [ ] 验证飞书群消息卡片渲染效果。

### Phase 2: 智能化升级 (下月)
- [ ] 接入 LLM API (如 Claude/OpenAI) 实现新闻摘要、去重、相关性打分。
- [ ] 增加多源 RSS 聚合逻辑，支持分类推送。
- [ ] 增加错误告警机制 (如抓取失败通知)。

### Phase 3: 平台化迁移 (3个月后评估)
- [ ] 评估 Python 脚本维护成本。若逻辑复杂度过高，迁移至 n8n。
- [ ] 部署 n8n Docker 环境，导入现有工作流逻辑。
- [ ] 利用 n8n 原生节点实现更复杂的分支逻辑 (如：仅推送高优先级新闻)。
